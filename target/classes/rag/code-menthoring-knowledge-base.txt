Session 1, Java and introduction to Spring Boot

Basic concepts and versions
- JVM: runs Java bytecode on any operating system.
- JDK: development kit (compiler and tools) that includes the JVM.
- JRE: libraries and components for running Java applications.
- Basic syntax (class, main method, System.out.println).
- Collections:
  - List: ordered collection that allows duplicates (for example, ArrayList).
  - Set: collection without duplicates (for example, HashSet).
  - Map: key-value pairs (for example, HashMap).
- Java evolution (mentioned milestones):
  - Java 8: lambdas, Streams API, Optional.
  - Java 11: var and new String APIs (local type inference).
  - Java 17: records and pattern matching (records as immutable and concise data holders).
  - Java 21: Sequenced Collections and Virtual Threads (mentioned as preview).

Lambdas, functional interfaces, and Streams
- Functional interface: an interface with a single abstract method, annotatable with @FunctionalInterface.
- Lambda: concise implementation of a functional interface (for example, name -> ...).
- Streams API:
  - Enables a pipeline for transformation and filtering (filter, map, collect, forEach).
  - Comparison (main points):
    - Streams: more readable and chainable, can be parallelized, but may introduce overhead and be harder to debug.
    - for: more control and easier debugging, generally more performant in simple cases, but more verbose and error-prone.

Spring Boot introduction
- Project creation via http://start.spring.io.
- Structure:
  - src/main/java: code.
  - src/main/resources: configuration.
- Example of a minimal API with @RestController and @GetMapping.

Suggested hands-on exercises
- Create a record for a product.
- Create a functional interface for discount calculation.
- Practice List, Set, and Map.
- Create a REST endpoint returning JSON.


REST concepts

What REST is
- REST: resource-based architecture (Representational State Transfer), described by Roy Fielding (2000).
- Characteristics: stateless, cacheable, layered system, uniform interface.

Semantic URIs
- Best practices:
  - Use nouns, preferably plural.
  - Avoid verbs in the URL.
  - Keep a clear hierarchy (for example, /api/v1/customers/5).

HTTP verbs and semantics
- GET: retrieve, typical return 200.
- POST: create, typical return 201.
- PUT: full update, return 200 or 204.
- PATCH: partial update, return 200.
- DELETE: remove, return 204.

Versioning
- Prefix endpoints with a version (for example, /api/v1).

Status codes (examples mentioned)
- 200 OK, 201 Created, 204 No Content, 400 Bad Request, 404 Not Found, 500 Internal Error.

Layered architecture in Spring
- Controller: HTTP.
- Service: business rules.
- Repository: persistence.
- Guideline: avoid putting logic in the Controller.


Using OpenAPI in Spring (springdoc)

Purpose and benefits
- Describe and document REST APIs in a standardized way.
- Automatic documentation generation, reducing manual work and drift.
- Swagger UI as an interactive interface.
- Helps define the contract between teams (frontend, mobile, third parties).

Spring Boot integration
- Dependency: springdoc-openapi-starter-webmvc-ui.
- Mentioned routes:
  - Swagger UI: /swagger-ui.html.
  - JSON spec: /v3/api-docs.

Customization
- Recommended annotations:
  - @Operation (summary, description).
  - @ApiResponse (codes and descriptions).
- Best practices:
  - @Schema on DTOs.
  - @Tag to group endpoints.
  - Document errors and response examples.
  - Possible contract validation (mentioned: Rest Assured + OpenAPI validator).


Docker, essential commands (starting point)

Images
- Build image via Dockerfile: docker build -t name:tag .
- Create image from a container: docker commit <container_id> name:tag
- List: docker images.
- Remove: docker rmi name:tag.

Containers
- Run interactively: docker run -it image-name.
- Run in background: docker run -d --name my-container image-name.
- Map a port: docker run -d -p 8080:80 image-name.

Management
- Active containers: docker ps.
- All containers, including stopped ones: docker ps -a.
- Stop: docker stop <container_id>.
- Remove: docker rm <container_id>.

Registry (Docker Hub)
- Login: docker login.
- Push: docker push user/name:tag.
- Pull: docker pull name:tag.

Cleanup
- docker image prune.
- docker system prune -a.


Spring, Beans, Singleton, and dependency injection

Singleton in Spring
- Concept: a single instance during the application lifecycle.
- Default pattern: Spring beans are singleton by default.

@Autowired (dependency injection)
- Role: ask Spring to inject a managed instance (usually a singleton) into the consuming class.

When it is not a Singleton
- Prototype scope: creates a new instance for each injection.


Testing in Spring Boot

Why test
- Ensure the code works and keeps working after changes.

Unit tests (JUnit 5 and Mockito)
- Test isolated units (for example, services).
- Mockito is used to mock dependencies (for example, repository).
- Common patterns: @Mock, @InjectMocks, when(...).thenReturn(...), assertions.

Integration tests
- @SpringBootTest:
  - Starts the full application context.
  - Used with @AutoConfigureMockMvc to test integrated endpoints.
- @WebMvcTest:
  - Starts only the web layer.
  - Services behind it are mocked with @MockBean.

What to validate in APIs
- HTTP status.
- Headers.
- Body (for example, jsonPath).

Complementary tools
- Postman: manual tests, exportable collections.
- RestAssured: fluent Java DSL for API testing.
- Testcontainers: bring real dependencies (PostgreSQL, Mongo, Kafka, etc.) up in containers during tests.

Final tips
- Start with unit tests, then move to integration tests.
- Prioritize critical rules.
- Use test names that describe behavior.
- If a test fails, fix the code, do not "massage" the test until it passes.


Spring Data JPA, relationships

One-to-Many and Many-to-One (Customer and Orders)
- @OneToMany(mappedBy = "...", cascade = CascadeType.ALL) on the "one" side.
- @ManyToOne on the "many" side.
- @JoinColumn defines the foreign key (for example, customer_id).

Many-to-Many (Student and Courses)
- Creates an intermediate table.
- @JoinTable defines the table and join columns.
- mappedBy indicates the mirrored side.

Important notes
- Identify the owner of the relationship (usually the side with @JoinColumn).
- cascade to propagate persistence.
- FetchType.LAZY (common in collections) to avoid loading everything at once and improve performance.


Session 4, Design Patterns and Mapper Pattern

Design Patterns, purpose and benefits
- Reusable solutions for common architecture and organization problems.
- Benefits: modularity, testability, maintainability, common vocabulary.

Mentioned patterns (typical use in Spring Boot APIs)
- Builder:
  - Objects with many attributes, fluent construction, avoids long constructors.
- Factory:
  - Centralizes object creation based on parameters, reduces coupling.
- Strategy:
  - Swap behavior through implementations, reduces if/else, makes extension easier (Open/Closed).
- Template Method:
  - Fixed flow with variable steps implemented by subclasses.

When not to use it
- Avoid overengineering; use a pattern only to solve a real problem.

Mapper Pattern (Data Mapper)
- Isolates conversion between entity/domain and DTO.
- Advantages: separates responsibility, avoids conversion in controller/service, makes testing easier.
- Short comparison:
  - Mapper: conversion between representations.
  - Adapter: adapts interfaces.
  - Decorator: adds behavior.
  - Factory: creates instances.
- Mentioned tools: MapStruct, ModelMapper (automate mapping).


Session 5, concurrency and processing models (MVC vs WebFlux)

Traditional model (Spring MVC with a server such as Tomcat)
- Thread pool (for example, the HTTP connector executor).
- Each request occupies one thread until the response is sent.
- If threads are busy: requests queue up; a full queue can generate 503.
- Blocking calls (DB, synchronous HTTP) keep the thread busy while waiting.

Reactive model (Spring WebFlux with Netty/Undertow)
- Event loop + non-blocking I/O.
- A small number of threads can serve many concurrent requests.
- Requires reactive programming (Mono, Flux, etc.).

Comparative summary
- MVC: simpler, but blocking and can saturate the thread pool.
- WebFlux: more scalable for high concurrency and non-blocking I/O, but increases complexity.
